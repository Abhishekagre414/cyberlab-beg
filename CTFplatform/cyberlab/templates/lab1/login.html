What actually happened

  • The homepage's rendered content looked ordinary — the interesting part was an HTML comment only visible via "View Page Source," containing base64-encoded basic-auth credentials for the backup archive.
  • Those credentials gated the /backup/ folder, but basic auth alone isn't real authorization — it was reachable by literally anyone who read the source.
  • The listing had a decoy file designed to waste time, plus the real expired file whose comment described the current naming convention — with the sensitive part (the environment name) ROT13-encoded so a casual glance wouldn't reveal it.
  • The actual production backup was never linked anywhere, but existed and was reachable once you knew its exact name.

How to prevent this for real

  • Never rely on client-visible artifacts (HTML comments, JS files, page source) to hold credentials, even "temporary" or "read-only" ones — treat anything shipped to the browser as public.
  • Basic auth on a static file directory is not a substitute for real, server-side authorization tied to identity and role.
  • Obfuscation (ROT13, base64) is not encryption and provides no real security — it only slows down automated scanning, not a determined human or a slightly-better scanner.
  • Delete backup artifacts entirely instead of rotating-and-keeping — a rotated credential in a file that still exists is still a map to your infrastructure.
