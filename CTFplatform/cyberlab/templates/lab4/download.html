What actually happened

  • The server did filename.replace("../", "") once, then joined the result onto the downloads folder path and opened whatever that produced.
  • A string like ....// doesn't present the exact substring ../ end-to-end the way a naive attempt would — but removing one matched ../ from the middle of it leaves the remaining characters forming ../ again, because the filter only ran once instead of repeating until no matches remained.
  • There was more than one sibling folder to try, and only reading the team's own public notes gave away which one actually held anything sensitive — the same way loose mentions in real internal docs/wikis often leak more than people realize.

How to prevent this for real

  • Never try to sanitize a path by stripping bad substrings — resolve the final path with os.path.realpath()/os.path.abspath() and verify it's still inside the intended base directory before opening it.
  • Better still: don't take raw filenames from users at all — map an opaque ID or an allowlisted key to a real filename server-side.
  • Be mindful of what casual internal notes reveal — folder names, tool names, and internal jargon are all reconnaissance value even when nobody meant them to be.
